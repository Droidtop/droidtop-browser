# Session lifetime decisions and static review, 2026-11-27

Owner request: "go through all the user-facing surfaces to see if they're usable" and include Droidtop Browser integration. Source-only audit; no local build or live browser/device interaction. Required recipe Android CI remains the compilation check.

## Bounded cookie bridge

`SessionCookies.send` previously retained every answer until a reply arrived. A connected-but-unresponsive extension or port disconnect could strand `WebViewActivity.finishWith`, which waits for its final cookie read before closing. Each request now answers once with a result or failure within ten seconds. A disconnected current port fails outstanding requests; late replies cannot call them again. A readiness timeout releases installation state so a later page can retry. This extends the existing ten-second installation deadline rather than adding a second unbounded wait.

## Cancellation and cleanup

The one-use `take_request` reply can arrive after its activity has been cancelled/destroyed. A valid late reply must be returned to Droidtop as incomplete instead of silently abandoning the token. A delayed extension-ready callback must not inject cookies into a cancelled activity. If injection was already sent when cancellation happened, successful completion removes the domains it installed. A failed injection ends the request incomplete rather than opening a page with an unknown session.

The cleanup domain set is shared between normal finish, destruction and injection cancellation: request domains plus download-site cookie keys. Previously destruction removed only request domains, leaving any injected download-site cookies behind.

## Boundaries and unverified gaps

- Host source: Droidtop `WebViewProviders.take` filters stored session cookies to request domains, adds approved download-site cookies, hands off a one-use token and imposes an overall ten-minute timeout. Its default-closed provider selection checks plugin approval and permission. Browser `DroidtopLink` pins Droidtop's signing certificate. The bridge runs only in Firefox's private cookie store.
- Native extension `background.js` already retries `connectNative` every second and says hello. Kotlin waits for `onPortConnected`, not a hello acknowledgement; actual Gecko handler registration/port sequencing needs a device trace. No speculative handshake change was made.
- Downloads are captured rather than saved, with per-resource cookie and user agent from Gecko's external-resource callback. The callback's provided response ownership/release behavior was not established from pinned upstream API source in this pass.
- The finish result reads `engine.settings.userAgentString`. Whether this is populated with Gecko's effective default identity on this pin is unverified. Reusing a stored WebView/Chrome identity in Gecko could invalidate browser checks; no guessed user-agent override was added.
- The initial lifecycle batch retained the existing shared private store. The embedded provider change below replaces that bridge with a per-session scoped origin-attribute API; actual Gecko isolation still needs a device trace.
- This activity handles many configuration changes in its manifest, but process death and unhandled configuration recreation have no restored one-use token/session ownership. The host eventually times out; recovery UX remains unresolved.
- Toolbar actions are horizontal, hardcoded English and not deeply reviewed for narrow screens, large fonts, pad focus or screen-reader semantics. Browser-check pass/fail behavior is a runtime question, not proven by compilation.

## Embedded surface (owner, 2026-11-27)

The owner clarified that the API must provide the view **and** contained/restricted information back, including downloads. On Android 11/API 30 and later the approved app runtime accepts the named `web.view.surface.v1` relay. Its typed AIDL and field/mode contract come from pinned `mytop-project/mytop-plugins` 0.3.3 (`android/aidl` and `android/web-surface-v1.json`), not local copies. The existing plugin `attachRelay` is the transport seam, not a JSON-encoded view or a script bridge. Browser checks Droidtop's pinned UID/certificate and loaded plugin identity on every provider call. Host death and plugin unload release view/session ownership.

Browser creates the real `EngineView` inside `SurfaceControlViewHost`; Droidtop supplies the display, dimensions and SurfaceView host token, fetches the `SurfacePackage` through an AIDL return value, and embeds it. `surfaceReady` is asynchronous and the provider's UI handoff for fetching the package is bounded to two seconds. Host calls must also run off the host UI thread with a deadline, since a synchronous Binder transaction itself can otherwise hang before the provider code runs. Return-value parcel flags and package release matter. The host forwards configuration (API 33+) and transfers accepted package ownership to SurfaceView.setChildSurfacePackage; only rejected or late packages are released by the host. The provider updates its local configuration context on resize, including API 30–32; Browser owns the view hierarchy and session. Older API levels and unavailable providers retain the activity path. Fallback must withdraw an **untaken** token; a taken request that fails ends incomplete, never replays.

One shared `WebSessionView` owns the activity and embedded page behavior. Typed JSON events are restricted to navigation/title/back availability, loading and stable errors. Cookies, user agent and captured download descriptors still return through `web.view.report_page`/`finish`, with the host enforcing approved domains and per-download header scope and owning vault updates/download transfers. Nothing exposes arbitrary script evaluation, DOM objects or file access. Every controller uses a fresh Gecko context. The privileged built-in cookie experiment requires the exact private flag and encoded session context on every query, insert and removal; it never addresses the user's global private store. Gecko 160 built-in-extension support, origin attributes, cookie manager and context encoding were checked in Mozilla release source. Mock tests verify cross-context confinement, domain/host-only filtering and refused unsafe input; actual engine roundtrip remains unverified.

Browse-only pages use a fresh random Gecko `contextId` and no cookie extension operations or cookie/UA/download export. Exact Firefox 160 release source verifies `Engine.createSession(private, contextId)`, `GeckoEngineSession` passing contextId to GeckoSessionSettings, `Core.geckoRuntime`, and `StorageController.clearDataForSessionContext`. The session closes before that context's storage is cleared. This is a separate Gecko context, not a claim that empty approved-domain lists alone isolate cookies.

Official references: [Android SurfaceControlViewHost](https://developer.android.com/reference/android/view/SurfaceControlViewHost), [SurfacePackage transfer and ownership](https://developer.android.com/reference/android/view/SurfaceControlViewHost.SurfacePackage), and [Firefox 160 Engine API](https://github.com/mozilla-firefox/firefox/blob/FIREFOX-ANDROID_160_0_RELEASE/mobile/android/android-components/components/concept/engine/src/main/java/mozilla/components/concept/engine/Engine.kt). Android describes SCVH as cross-process View hierarchy embedding; this is why a raw drawing Surface was insufficient for IME and accessibility. Actual Gecko nested-surface rendering, text input/composition, selection/popup windows, touch/pad, accessibility, resize/density and provider death need a rig check. Compilation alone cannot prove those work.

## Needs a rig check

## Body download handoffs

The v2 relay explicitly announces `web.download.body.v1` and `web.browse.isolated.v1` through `connectedCapabilities`; v1 retains the original method prefix and never receives body callbacks. The host validates/reserves each opaque offer, then acknowledges it with `offerResult`. Only accepted offers become `{streamOfferId}` descriptors in `finish`. An HTTP(S) page address in the metadata is provenance, never a fallback retrieval address. Browser supplies the actual Gecko `Response.body` through a one-use reliable pipe; it does not turn a blob or POST response into a new GET. At most 16 offers per page and 32 per relay, four copy workers, 64 GiB, 60-second unclaimed/stalled limits and a 60-minute total limit bound provider resources. Host applies job/free-space limits and owns the destination. Reliable-pipe errors, explicit cancellation and host death release the body. Independent host relays coexist; opening another page does not revoke prior body leases. An idle relay is removed after its page and offers drain. Plugin unload or host death explicitly fails its outstanding transfers rather than silently refetching.

Accepted bodies retain their GeckoSession and scoped context even after the UI/result closes, until every body is transferred, cancelled or expired. The view detaches immediately. This avoids assuming that closing GeckoSession leaves its response stream readable. URL-only callbacks remain HTTPS retrieval handoffs; a non-replayable URL without a supplied transferable response shows an explicit error and is never counted as captured. The legacy activity path cannot offer PFD bodies and shows that limitation instead of falsely claiming success. A refused finish result has terminal Close/start-again feedback because the host consumes the token before validation. Failed readback offers Retry while retaining the earned session and context; failed startup also has a recoverable error surface. No success is inferred from a rejected broker result.

Additional rig checks: blob/data and POST-generated downloads, end-to-end byte/hash equality, unknown and incorrect lengths, pipe EOF/error propagation, backpressure, delayed job start, host cancellation/restart, provider death, offer expiry, and finish-before-transfer session retention. Standard authentication cookie/UA roundtrip and multiple simultaneous scoped sessions must also be exercised. This source/CI work is not evidence those flows already work on the device.

## Independent activity download compatibility follow-up

Pinned Gecko 160's external-response callback supplies a Response for ordinary GET downloads too, without exposing the original request method. The initial surface implementation correctly refused to guess a replayable GET when no body-capable surface host existed, but that also left API 26–29 activity fallback downloads unsupported on new hosts. The body-only `web.download.body.v1` relay now supplies the same acknowledged one-use PFD transfer without any SurfacePackage or surface-interface dependency in its AIDL, endpoint or body registry. Canonical `mytop-plugins` owns those interfaces/metadata; the surface v1/v2 transactions remain unchanged.

The host establishes the verified plugin endpoint before launching an OPEN activity/taking its request. The activity resolves that endpoint after its broker handshake, and retains the selected transport for any accepted body leases. Bodies keep the existing size/time/concurrency limits, session/context lease, acknowledgement and host-owned download/vault boundary. Ordinary GET, POST and blob responses use the supplied bytes; a non-replayable source is never refetched as a GET. Old hosts without the capability see an explicit Update Droidtop message and no misleading retry or captured download success. API26 runtime loading, activity finish before transfer, provider death, delayed transfers and host-version combinations still require rig checks.

## Legacy cookie attribute fidelity

The broker/vault currently transports only Cookie header strings, which have lost Domain, Path, HttpOnly, SameSite and expiry metadata. Importing those as domain cookies or JavaScript-readable cookies would broaden the original authority. Unknown imported cookies therefore use exact-host, HttpOnly, Secure, SameSite=Lax, session-only defaults at the root path. Root-path storage is the existing header contract's limit, not a claim the original path is known. Site-created cookies inside the scoped Gecko context retain their original attributes, but exporting a header and reimporting later still loses that fidelity. JavaScript-readable CSRF cookies may consequently require fresh sign-in; this compatibility question needs site checks and must not be guessed by cookie name.

Full fidelity needs optional structured cookie records across `web.view.take_request`/`finish`, WebSessions.Stored and the encrypted vault: name/value, exact host versus Domain scope, path, Secure, HttpOnly, SameSite, expiry/session state, plus an explicit policy for partitioned cookies. The host must validate every record against approved sites, prohibit widening authority, bound counts/size, keep session-context identifiers internal, and preserve a conservative legacy fallback. That cross-broker/vault format is a remaining gap, not implemented by fabricating attributes from raw headers.
